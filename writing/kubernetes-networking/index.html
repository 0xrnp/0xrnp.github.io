How a request reaches a Kubernetes pod

Rudra Narayan Panda · 19 Nov 2026

Pods come and go, and their IP addresses go with them. Kubernetes networking is the set of pieces that give clients a stable address anyway. This is the second of two posts. The first covers what runs where. This one follows a request in, and covers two changes in 2026 that older guides miss.

every pod gets an IP

The Kubernetes network model says each pod has its own IP address, and any pod can reach any other pod without NAT. Kubernetes only states the rule. A network plugin (CNI), such as Calico, Cilium or Flannel, does the wiring, and the container runtime calls it to set up the pod's network when the pod starts.

services give pods a stable address

A Service has a virtual IP (the ClusterIP), a DNS name such as web.default.svc.cluster.local, and a label selector. The pods that match the selector are listed in EndpointSlices, each with a ready flag:

kubectl get endpointslices -l kubernetes.io/service-name=web

In iptables and nftables mode, the ClusterIP is not on any network interface. kube-proxy runs on every node, watches Services and EndpointSlices, and programs the node's packet filter so traffic to the ClusterIP is rewritten to the IP of one ready pod. Pods whose endpoint is not ready are skipped. Without that rewrite, the address leads nowhere. Some network plugins, Cilium for one, can replace kube-proxy and do this themselves.

kube-proxy has three modes on Linux, and one is on its way out

modestatus
iptablesThe default. It works everywhere, and the rules slow down as the number of Services grows.
nftablesGA since v1.33. It needs Linux kernel 5.13 or later. It is the recommended choice, and you have to select it yourself because clusters do not switch on upgrade.
ipvsDeprecated since v1.35. SIG Network wrote on 16 Nov 2026 that it plans to remove it in v1.40, and recommends nftables for v1.36 and later.

If you run IPVS, plan the move to nftables. In a kubeadm cluster that means setting mode: nftables in the kube-proxy ConfigMap and restarting kube-proxy. IPVS-specific options need to be mapped across by hand. The announcement is linked at the end.

service types

typewhat it adds
ClusterIPThe virtual IP, reachable only inside the cluster. The default.
NodePortAlso opens a port on every node (30000 to 32767 by default) that forwards to the Service.
LoadBalancerAlso asks the cloud provider for an external load balancer pointing at the Service.
ExternalNameNo proxying. The Service name resolves to a DNS name you give it.

layer 4 and layer 7

A Service works at layer 4. It sees an IP address and a port, over TCP or UDP, and nothing of the HTTP request inside. It cannot send /api to one Service and /static to another, or choose by hostname, or terminate TLS for several domains. That is layer 7 work, and it needs something that reads HTTP: an Ingress controller or a Gateway API implementation, running as pods in your cluster behind a LoadBalancer or NodePort Service.

ingress is frozen, and ingress-nginx is retired

The Ingress API is still GA, but it is feature-frozen, and new development has moved to the Gateway API. The most widely used controller, the community ingress-nginx, was retired. SIG Network announced on 11 Nov 2025 that maintenance would end in March 2026. After that date there are no more releases, bug fixes or security updates. Existing deployments keep running, but nothing patches them. The retirement covers that one project. Other Ingress controllers are separate projects, and they are not part of it.

The Gateway API, whose core resources have been GA since October 2023, is the recommended replacement. It splits what Ingress puts in one object. A platform team owns the Gateway (the listener, the addresses, the TLS), and each app team owns an HTTPRoute that attaches to it:

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
spec:
  parentRefs:
    - name: public-gateway
  hostnames: ["example.com"]
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: api
          port: 80

where it breaks

symptomcheck
Service name does not resolve, pod IP worksDNS: the CoreDNS pods, and the pod's /etc/resolv.conf.
Service resolves but connections failkubectl get endpointslices -o yaml. No endpoints means the selector matches nothing. Endpoints with ready: false mean no pod is ready yet.
LoadBalancer stays <pending>Whether a cloud controller or load balancer implementation is installed, and the cloud quota.
404 from the gatewayThat the route is attached to the Gateway, and that the hostname and path match the request.
NodePort answers on some nodes onlyThe Service's externalTrafficPolicy. With Local, only nodes that run a matching pod answer.
